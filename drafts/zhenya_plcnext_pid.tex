\section{PLCnext and AXC F 2152}

The neuro-symbolic controller must satisfy two requirements that are normally
met by two different machines. The PID loop that holds the pasteurization
temperature has to close within a fixed cycle, which is the domain of a
programmable logic controller (PLC). The neural adjuster that retunes that loop,
and the client that queries the ontological knowledge base, are ordinary
user-space programs and expect a general-purpose operating system. PLCnext
Control satisfies both in a single device. It runs a real-time Linux in which
the Execution and Synchronization Manager schedules IEC 61131-3 tasks and native
C++ components within the same cycle~\cite{PLCnextControl}. An adjuster written
in C++ therefore executes beside the PID loop rather than on a supervisory PC,
and no network hop separates adaptation from control.

The pasteurization unit is controlled by an \textbf{AXC F 2152} supplied as part
of a PLCnext Technology Starterkit (Fig.~\ref{fig:ACXF2152}). The kit adds AXL
SE DI16/DO16/AI4 modules and a slide potentiometer to the controller, which is
enough to reproduce the temperature loop on the bench before the code is moved
to the plant.

Table~\ref{tab:axcf2152} lists the properties of the controller that constrain
the design of the adjuster. Two of them are decisive. The dual-core 800~MHz
processor evaluates the forward pass of a 20-10-3 perceptron in a small fraction
of the temperature-loop cycle, so inference is not the limiting factor. The
internal mass storage holds the weight file, the telemetry collected from the
unit, and the OSTIS client without an external card.

\subsection{Toolchain and deployment}

Development is cross-platform. The adjuster is written and debugged in Visual
Studio 2022 on a workstation and built for the ARM target of the controller.
Three components make the cross-build possible: CMake as the build system, the
PLCnext command line interface (\textbf{plcncli}) as its driver, and the SDK
matching the firmware version of the controller. The SDK is installed once:

\begin{lstlisting}[basicstyle=\ttfamily\small,breaklines=true,breakatwhitespace=true]
plcncli.exe install sdk -d [installation path] -p [path to archive file]
\end{lstlisting}

The PLCnext Technology extension for Visual Studio supplies the project
templates and a remote debugger, so a breakpoint can be set in the adjuster
while the loop runs on the unit. This is the reason the environment was chosen
over a bare CMake toolchain.

The resulting binary reaches the controller by one of two routes. PLCnext
Engineer performs network configuration, code download, HMI and OPC UA
configuration within one project, and is appropriate when the deployment
accompanies a change in the IEC 61131-3 program. When only the adjuster changes,
a plain SFTP transfer over SSH is faster and needs no project file; PuTTY and
WinSCP cover this case. Both routes were used during commissioning.

\subsection{Coupling the controller to the knowledge base}

A neural adjuster on its own is a black box, and a black box is difficult to
justify in food processing, where the temperature-time profile of the product is
a safety requirement rather than a quality target. The knowledge base supplies
the symbolic half of the loop. The resulting runtime split is shown in
Fig.~\ref{fig:zhenya_plcnext_ostis}: the real-time task carries the control law,
the Linux user space carries the client that talks to the OSTIS server, and the
two exchange only the three gains and the current operation.

The controller is bound to the ontological description of the plant at three
points. First, every signal of the loop carries the identifier that ISA-5.1
assigns to it in the EPLAN documentation generated by
EasyEPLANner~\cite{EasyEPLANner}; the same identifier names the corresponding
element in the knowledge base, so a measurement in the real-time task and a
concept in the base denote one object. Second, the loop is declared in the base
as a control module of the pasteurization unit in the sense of
ISA-88~\cite{ISA88}, which places it under the unit procedure that the recipe is
currently executing. Third, the admissible range of the three gains is treated
as an attribute of that procedure rather than a property of the network. During
holding, the base restricts the adjuster to a narrow band around the
commissioned values; during heat-up, it widens the band. The network proposes,
the knowledge base authorizes.

This split changes what the system can report. When the temperature deviates,
the answer available to the operator is not a vector of weights but a statement
assembled from the base: which unit, which operation, which control module, and
which limits were in force. The controller reuses the web query interface of the
OSTIS server rather than hosting a reasoner of its own, so no additional service
runs on the device. The client issues an HTTP request from user space, and the
real-time task is not disturbed.

\section{Developed Neuro-PID controller}

The pasteurization unit is a plant with a variable transport delay. The product
flow rate changes between batches, the plate heat exchanger fouls between
washes, and the temperature of the heat carrier follows the steam header. A
single set of PID coefficients is therefore a compromise across operating
points, and the compromise is worst exactly where the process is most sensitive:
at the transition into holding.

The controller developed for the unit keeps the conventional discrete PID law at
the point of action and moves the tuning problem into a neural network. The
network does not compute the control action; it supplies the three coefficients
from which the action is computed, at every step. This is the arrangement now
common in the literature on adaptive neural
tuning~\cite{Almachi2025, Zribi2025, Ito2025pinn}, and it is the reason a neural
component is admissible in food processing at all: the network changes the
parameters of the law, not the law itself. The overall structure is shown in
Fig.~\ref{fig:neuro_PID_controller}, where the outputs of the neural network
(NN) are the proportional gain $K$, the integral time $T_I$, and the derivative
time $T_d$~\cite{ivaniuk2013neuro}.

\subsection{Control law}

The PID part of the controller is written in incremental form,
Eq.~\ref{PID_algorithm}~\cite{ivaniuk2013neuro}. Here $u_n$ is the action
applied to the plant at the instant $t = n T_0$, $e_n = r_n - y_n$ is the
deviation of the measured temperature $y_n$ from the setpoint $r_n$ dictated by
the recipe, and $T_0$ is the sampling interval. The coefficients $q_0$, $q_1$
and $q_2$ are never tuned directly. They are recomputed from the proportional
gain $\mathbf{K}$, the integral time $T_I$ and the derivative time $T_D$
whenever the adjuster delivers a new triple, which keeps the tuning problem in
the units an engineer reads on the panel.

\begin{equation}\label{PID_algorithm}
  \begin{aligned}
    u_k  & = u_{k - 1} + \Delta u_k,                                         \\
    \Delta u_k & = q_0 e_k + q_1 e_{k - 1} + q_2 e_{k - 2},                  \\
    q_0  & = \mathbf{K}\left(1 + \frac{T_D}{T_0}\right),                     \\
    q_1  & = -\mathbf{K}\left(1 + 2\frac{T_D}{T_0} - \frac{T_0}{T_I}\right), \\
    q_2  & = \mathbf{K}\frac{T_D}{T_0}.
  \end{aligned}
\end{equation}

The incremental form matters on this plant for a practical reason. The action is
accumulated from increments rather than recomputed from an integral, so a change
of gains between two steps does not produce a jump in the valve position. The
adjuster may therefore update the triple during a batch without an explicit
bumpless-transfer scheme.

\subsection{Neural adjuster}

The adjuster is a multilayer perceptron with 20 input, 10 hidden and 3 output
elements; the hidden and output layers use the sigmoid activation function. Its
inputs are the recent history of the loop, formed by the delay operators TD in
Fig.~\ref{fig:neuro_PID_controller}: past deviations, past control actions and
past measurements. Its outputs are the three gains. The network therefore
observes how the loop has been behaving and answers with the tuning that the
next steps require.

Equation~\ref{PID_nn} describes one training step~\cite{ivaniuk2013neuro}. The
first line is the forward pass through an element with weights $\omega_{ij}$ and
threshold $T_j$; the second and third lines propagate the error backwards from
the output layer to the hidden one; the fourth and fifth lines update weights
and thresholds with the learning rate $\alpha$; the last line is the accumulated
error over $L$ stored samples.

\begin{equation}\label{PID_nn}
  \begin{aligned}
    y_j       & = F(\sum_{i}{\omega_{i j}y_i - T_j}),                         \\
    \gamma_j  & = y_j - t_j,                                                  \\
    \gamma_i  & = \sum_{i}{\gamma_iF^\prime(S_i)\omega_{j i}},                \\
    \omega_{i j}(t + 1) & = \omega_{i j}(t) - \alpha\gamma_jF^\prime(S_j)y_i, \\
    T_j(t + 1)& = T_j(t) + \alpha\gamma_jF^\prime(S_j),                       \\
    E         & = \frac{1}{2}\sum_{k = 1}^{L}{\sum_{j}{({y_j}^k} - {t_j}^k)^2}.
  \end{aligned}
\end{equation}

Back-propagation needs a differentiable objective, and no reference triple of
gains exists against which the outputs could be compared. The control error
itself is used instead: at the instant $t = n T_0$ the objective is $E_n =
\frac{1}{2}e_n^2$. Minimizing it over a single sample would make the adjuster
follow the noise of the resistance thermometer, so a window of previously stored
values $E_{n-p}, \dots, E_{n-2}, E_{n-1}, E_n$ is retained, where $p$ sets how
many past images take part in the update~(\ref{PID_nn}). The update then depends
on a trajectory rather than on one measurement.

Both the control law and the adjuster execute inside a single task of the
Execution and Synchronization Manager, so the gains in force at step $n$ are the
gains the network produced from the history ending at step $n-1$. The weights
are held in memory during a batch and written to internal storage at its end,
which keeps the file system out of the real-time path. Surveys of industrial
machine learning identify precisely this boundary --- what runs in the control
cycle and what runs beside it --- as the practical constraint on deploying
learned components in process industries~\cite{Lawrence2024}.
